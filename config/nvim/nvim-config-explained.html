How This Neovim Config Works

A file-by-file, function-by-function walkthrough of ~/.config/nvim (really ~/.bin/dotfiles/config/nvim, symlinked in).

How it loads

Neovim starts by running init.lua. Everything else is pulled in from there, in this order:

1. vim.loader.enable()      -- byte-compile cache, speeds up every later require()
2. config.options            -- vim.opt settings, must run before plugins (sets mapleader)
3. config.lazy               -- bootstraps lazy.nvim, which loads lua/plugins/*.lua
4. config.keymaps            -- global keymaps (some lazy-require plugins on first use)
5. config.commands           -- :WQ / :Wq / :W / :Q / :Ggu user commands
6. config.autocmds           -- cursor-restore, filetype detection, new-file templates

Separately, whenever you open a .java or .py file, Neovim automatically runs after/ftplugin/java.lua or after/ftplugin/python.lua — this is a built-in convention (any file under after/ftplugin/<filetype>.lua runs on FileType <filetype>), not something wired up by hand anywhere.

Why plugins live in lua/plugins/ as separate files: lazy.lua calls require("lazy").setup({ spec = { { import = "plugins" } } }). The import = "plugins" line tells lazy.nvim to require() every module under lua/plugins/ and treat whatever table each one returns as a plugin spec. That's the entire mechanism — there's no manual list of plugins anywhere to keep in sync.

core init.lua

The single entry point. Deliberately tiny — just enables the bytecode loader and requires the six config.* modules in the order that matters.

vim.loader.enable()

require("config.options")
require("config.lazy")
require("config.keymaps")
require("config.commands")
require("config.autocmds")
  • vim.loader.enable() turns on Neovim's byte-compilation cache for all require()d Lua modules (both this config's and every plugin's). Every subsequent load reads compiled bytecode from ~/.local/state/nvim/luac instead of re-parsing source — this is most of why cold startup is ~20ms instead of ~150-200ms.
  • Order matters: options must run before lazy because it sets vim.g.mapleader, and lazy.nvim needs the leader key defined before it evaluates any plugin spec that maps a leader-prefixed key.
  • keymaps runs after lazy so that keymaps referencing plugin modules (e.g. require("telescope.builtin")) are defined once lazy.nvim's module-require hook is active.

core lua/config/options.lua

Everything from the old .vimrc's set lines, translated to vim.opt, plus a few new settings for plugins added along the way.

Leader key

vim.g.mapleader = ","

Set first, before anything else in the file, because it has to exist before any <leader>... keymap (here or in any plugin spec) is registered.

Basic editing settings

local opt = vim.opt

opt.hlsearch = true          -- highlight all search matches
opt.incsearch = true         -- highlight while typing the search
opt.number = true            -- show absolute line number on current line
opt.relativenumber = true    -- relative numbers on every other line (for 3j / 5k)
opt.cursorline = true         -- highlight the current line
opt.tabstop = 2
opt.softtabstop = 2
opt.shiftwidth = 2
opt.expandtab = true          -- tabs insert spaces (2 by default; java/python override to 4)
opt.ttimeoutlen = 0          -- no delay after Esc in key sequences
opt.smartcase = true
opt.smartindent = true
opt.ignorecase = true
opt.complete:remove("i")     -- don't scan included files for keyword completion (slow)
opt.splitright = true         -- vertical splits open to the right
opt.autoread = true           -- reload a file if it changes on disk
opt.errorbells = false
opt.shell = "/bin/zsh"
opt.iskeyword:remove("_")    -- underscore is a word *boundary*, not part of a word
opt.hidden = true             -- allow switching buffers without saving first

All ported 1:1 from the equivalent set lines in .vimrc. The two :remove()/:append()-style calls exist because complete, iskeyword, and wildignore are Vim's comma/flag-separated "list-like" options — vim.opt wraps them in an object with :append()/:remove()/:prepend() methods instead of requiring manual string concatenation.

Ripgrep / fzf environment

vim.env.RIPGREP_CONFIG_PATH = vim.env.HOME .. "/.ripgreprc"
vim.env.FZF_DEFAULT_COMMAND = 'rg --files --hidden --glob "!.git"'

opt.wildignore:append({ -- ~20 patterns: .git, target/, *.class, *.pyc, images, etc.
  "*/.git/*", "*/.hg/*", -- ...
})

if vim.fn.executable("rg") == 1 then
  opt.grepprg = "rg --vimgrep --smart-case --hidden"
  opt.grepformat = "%f:%l:%c:%m"
end

FZF_DEFAULT_COMMAND is kept even though Telescope replaced fzf.vim as the picker — it's harmless to leave set, and useful if you ever shell out to real fzf from a terminal. grepprg/grepformat back the plain :grep command used by <leader>g (see keymaps.lua), which populates the quickfix list rather than opening a picker — different workflow from Telescope's live_grep, kept for when you want quickfix-list navigation (:cnext/:cprev) instead of a picker.

Folding

-- Treesitter (lua/plugins/treesitter.lua) enables fold-by-expression, which
-- defaults to closing every fold (functions included) as soon as a file
-- opens. foldlevelstart=99 keeps everything open by default while leaving
-- manual folding (za/zc/zo) fully working.
opt.foldlevelstart = 99

This exists specifically because treesitter's fold-by-expression (set up in treesitter.lua) closes every fold by default the moment a buffer with a fold method opens — foldlevelstart is Neovim's "how many fold levels to leave open when a window is first displayed" setting; 99 is comfortably higher than any realistic nesting depth, so everything starts expanded. za/zc/zo still work normally for manual folding.

Persistent undo

local undodir = vim.fn.expand("~/.vim/undo")
vim.fn.mkdir(undodir, "p")
opt.undodir = undodir
opt.undofile = true

Same undo directory the old .vimrc used, so undo history from vim sessions carries over. vim.fn.mkdir(..., "p") is the Lua equivalent of the old silent !mkdir -p line — creates the directory (and parents) if it doesn't exist, without shelling out.

core lua/config/lazy.lua

Bootstraps the lazy.nvim plugin manager and hands it the entire lua/plugins/ directory.

local lazypath = vim.fn.stdpath("data") .. "/lazy/lazy.nvim"
if not vim.uv.fs_stat(lazypath) then
  vim.fn.system({
    "git", "clone", "--filter=blob:none",
    "https://github.com/folke/lazy.nvim.git",
    "--branch=stable",
    lazypath,
  })
end
vim.opt.rtp:prepend(lazypath)

Self-installing: if lazy.nvim itself isn't cloned yet (first run on a fresh machine), this shells out to git clone before requiring it. --filter=blob:none is a partial-clone flag that skips downloading file contents for history you don't need yet, keeping the clone fast. vim.opt.rtp:prepend(lazypath) puts lazy.nvim's own Lua files on the runtime path so require("lazy") below can find them.

require("lazy").setup({
  spec = { { import = "plugins" } },
  install = { colorscheme = { "tokyonight" } },
  checker = { enabled = false },
  performance = {
    rtp = {
      disabled_plugins = {
        "gzip", "tarPlugin", "tohtml", "tutor", "zipPlugin",
      },
    },
  },
})
  • spec = { { import = "plugins" } } is the whole plugin-discovery mechanism: it tells lazy.nvim to require every file in lua/plugins/ and collect whatever spec table each one returns.
  • install.colorscheme is only used as a fallback during the very first install, if lazy.nvim needs to pick something to display before plugins finish downloading.
  • checker.enabled = false turns off lazy.nvim's background "check for plugin updates" polling — a small but real startup/idle-CPU cost with no benefit for a config you update manually.
  • disabled_plugins removes a handful of Neovim's bundled runtime plugins (gzip file editing, tar/zip archive browsing, the built-in tutor, HTML conversion) that add to startup scanning cost and are never used here.

core lua/config/keymaps.lua

All global (non-filetype-specific) keymaps: ported 1:1 from .vimrc's mapping section, plus everything added for LSP/Telescope/gitsigns/toggleterm.

Telescope-backed search (replaces fzf.vim)

map("n", "<C-p>", function() require("telescope.builtin").find_files() end)
map("n", "<leader>f", function() require("telescope.builtin").live_grep() end)

Each mapping is a closure that calls require("telescope.builtin") only when the key is actually pressed — not at config-load time. That matters for startup speed: because these require() calls are deferred, lazy.nvim never has to load Telescope until you actually press <C-p> or <leader>f for the first time (lazy.nvim hooks Lua's module loader so that requiring any of a lazy-loaded plugin's modules transparently triggers loading it).

format_buffer() — behind <leader>l

local function format_buffer()
  local ft = vim.bo.filetype
  if ft == "java" then
    vim.lsp.buf.format({ async = false })
  elseif ft == "python" then
    local ok, conform = pcall(require, "conform")
    if ok then
      conform.format({ lsp_fallback = false })
    end
  else
    vim.cmd('normal! mqggVGgq`q')
  end
end

One key, three different formatting strategies depending on filetype:

  • Java: vim.lsp.buf.format() asks whatever LSP client is attached (jdtls) to format the buffer using Eclipse JDT's built-in formatter.
  • Python: delegates to conform.nvim, which runs black over the buffer. pcall guards against conform not being loaded yet.
  • Everything else: falls back to the exact macro the old .vimrc used for <leader>l: mq (set mark q) → gg (top) → VG (select to bottom) → gq (reformat via formatprg/textwidth) → `q (jump back to mark q). This preserves the old behavior for any filetype that isn't explicitly handled.

try_tag_jump(word)

local function try_tag_jump(word)
  local ok = pcall(vim.cmd, "tag " .. word)
  if not ok then
    vim.notify("No tag found for '" .. word .. "', searching instead", vim.log.levels.INFO)
    fn.search_current_word()
  end
end

A shared helper used by both ctags-fallback paths below. Plain :tag <word> throws E426: Tag not found when the word under the cursor isn't in the tags file — without pcall, that surfaced as a raw uncaught error rather than failing quietly. This matters most in non-Java files: there's no LSP to take the primary path, so this ctags fallback runs on every <leader>]/<C-]> press, and any word that isn't in the tags file (which is most words, most of the time) hit the raw error.

Rather than just swallowing the error, the failure case now chains into the exact same search <leader>w uses (fn.search_current_word() — Telescope grep for the word, with the underscore-in-identifiers iskeyword handling that function already does). So a failed "jump to definition" still does something useful: it shows you every place that word actually appears in the project, which is often good enough to answer "where is this defined/used" even without a tags entry or an LSP. Verified: triggering the fallback opens a real TelescopePrompt buffer seeded with the word, for both <leader>] and <C-]>.

goto_definition() — behind <leader>]

local function goto_definition()
  if #vim.lsp.get_clients({ bufnr = 0 }) > 0 then
    vim.lsp.buf.definition()
  else
    local word = vim.fn.expand("<cword>")
    if word ~= "" then
      try_tag_jump(word)
    end
  end
end
map("n", "<leader>]", goto_definition)

<leader>] and <leader>[ used to be buffer-prev/next in the old vimrc — redundant with Tab/Shift-Tab, which do the same thing. <leader>] was repurposed for go-to-definition: if any LSP client is attached to the current buffer, ask it where the symbol under the cursor is defined; otherwise fall back to Vim's native :tag command via try_tag_jump above, which looks the word up in the tags file generated by ctags. This means the same key works whether or not a language server is running.

jump_back() — behind <leader>[

local function jump_back()
  local ok = pcall(vim.cmd, "pop")
  if not ok then
    vim.api.nvim_feedkeys(vim.api.nvim_replace_termcodes("<C-o>", true, false, true), "n", false)
  end
end
map("n", "<leader>[", jump_back)

The companion to <leader>]: undoes the last jump. Every :tag-family jump (which is what both vim.lsp.buf.definition() and the plain :tag fallback ultimately push onto) records an entry on Vim's tag stack, separate from the regular jumplist. :pop pops the most recent entry off that stack and returns you to where you were before the jump — wrapped in pcall because :pop throws an error (E555/E73) if the stack is empty, which happens right at the start of a session before you've jumped anywhere yet. When that happens, it falls back to Neovim's plain jumplist instead (<C-o>, "older position"), fed via nvim_feedkeys since <C-o> isn't a : command that vim.cmd can run directly. Verified both paths: popping the tag stack after a <leader>] jump returns to the exact line the jump started from, and triggering it with an empty stack falls through cleanly with no error.

goto_definition_or_references() — behind <C-]>

A smarter variant of the same idea, added after testing showed plain go-to-definition alone wasn't enough — this one also answers "where is this used?":

local function goto_definition_or_references()
  local clients = vim.lsp.get_clients({ bufnr = 0 })
  if #clients == 0 then
    -- no LSP: plain ctags jump, same as <leader>]
    local word = vim.fn.expand("<cword>")
    if word ~= "" then try_tag_jump(word) end
    return
  end

  local client = clients[1]
  local params = vim.lsp.util.make_position_params(0, client.offset_encoding)
  vim.lsp.buf_request(0, "textDocument/definition", params, function(err, result)
    if err or not result or vim.tbl_isempty(result) then return end

    local target = result[1] or result
    local target_uri = target.uri or target.targetUri
    local target_range = target.range or target.targetSelectionRange

    local already_there = target_uri == vim.uri_from_bufnr(0)
      and target_range.start.line == vim.fn.line(".") - 1

    if already_there then
      require("telescope.builtin").lsp_references()
    else
      vim.lsp.util.show_document(target, client.offset_encoding, { reuse_win = true, focus = true })
    end
  end)
end
map("n", "<C-]>", goto_definition_or_references)

Step by step:

  1. Send a raw textDocument/definition LSP request by hand (rather than the higher-level vim.lsp.buf.definition()), because the callback needs to inspect where the definition is before deciding what to do.
  2. The result is a Location or LocationLink — the two shapes use different field names (uri/range vs. targetUri/targetSelectionRange), so both are checked with or.
  3. The key comparison: is the definition's file and line the same as where the cursor already is? If you pressed <C-]> while standing on a usage of a symbol, the definition is somewhere else → jump there. If you pressed it while already standing on the definition itself, jumping would be a no-op — so instead it opens a Telescope picker listing every place that symbol is referenced.
  4. Jumping uses vim.lsp.util.show_document(...) rather than the older jump_to_location(), which Neovim 0.12 marked deprecated in favor of show_document.
Why not just always show references on a second press? Because "second press" isn't tracked state anywhere — this check is stateless and re-derived every single time from cursor position vs. definition location, which is simpler and can't get out of sync.

vim.api.nvim_create_user_command("Ggu", function(opts)
  vim.cmd('!zsh -c "source ~/.zshrc && ggu ' .. (opts.args ~= "" and opts.args or "") .. '"')

In command-line mode, typing %% expands to the current file's directory. Handy for e.g. :e %% to open a file browser in the same directory as the file you're editing.

core lua/config/autocmds.lua

Everything from the old augroup MyVimrc: quickfix-after-grep, cursor restore, filetype detection for a few extensions, and new-file templates.

local group = vim.api.nvim_create_augroup("MyVimrc", { clear = true })

clear = true matters if this file ever gets re-sourced (e.g. via <leader>rr): it wipes any previously-registered autocmds in this group first, so re-running the file doesn't register the same autocmd twice.

Cursor restore

vim.api.nvim_create_autocmd("BufReadPost", {
  group = group,
  callback = function()
    if vim.bo.filetype:match("commit") then return end
    local mark = vim.fn.line("'\"")
    if mark > 0 and mark <= vim.fn.line("$") then
      vim.cmd('normal! g`"')
    end
  end,
})

Every buffer gets a '" mark automatically, recording the cursor position from the last time it was closed. This jumps back to it on reopen, skipping commit-message buffers (where you always want to start at the top). The line-number bounds check (mark > 0 and mark <= line("$")) guards against a stale mark pointing past the end of a file that's since shrunk.

Filetype detection + templates

local ft_patterns = {
  { "*.feature", "cucumber" }, { "*.zconfig", "zsh" },
  { "*.config", "sh" },      { "*.ejs", "html" },
  { "*.cmd", "markdown" },  { "*.j2", "yaml" },
}
for _, entry in ipairs(ft_patterns) do
  vim.api.nvim_create_autocmd({ "BufRead", "BufNewFile" }, {
    group = group, pattern = entry[1], command = "setfiletype " .. entry[2],
  })
end

A data-driven loop instead of six separate autocmd lines — same effect as the original vimrc, just generated. Then two more autocmds prefill new .sh/.py files from skeleton templates in ~/.bin/dotfiles/skeletons/ (a shebang line, boilerplate, etc.) the moment you create one.

core lua/config/functions.lua

Lua ports of every custom Vimscript function from the old .vimrc. Returns a table (M) of functions that keymaps.lua wires up to keys.

M.insert_current_time()

function M.insert_current_time()
  local current_time = os.date("!%Y-%m-%dT%H:%M:%SZ")
  vim.fn.append(
    vim.fn.line("."),
    string.format('private static final Instant NOW = Instant.parse("%s");', current_time)
  )
end

Bound to <leader>nt. Inserts a ready-to-paste Java Instant constant with the current UTC time — useful for fixed-clock test setup. os.date("!...") — the leading ! forces UTC rather than local time.

generate_uuids(count), M.insert_uuid(), M.insert_uuids_visual()

local function generate_uuids(count)
  local out = vim.fn.system(string.format('zsh -c "source ~/.zshrc && ggu %d"', count))
  local uuids = {}
  for line in out:gmatch("[^\r\n]+") do table.insert(uuids, line) end
  return uuids
end

Shells out to the same ggu zsh function used by :Ggu, requesting count UUIDs at once, then splits the output into a Lua list by newline.

function M.insert_uuid()
  local uuids = generate_uuids(1)
  if uuids[1] then vim.api.nvim_put({ uuids[1] }, "c", true, true) end
end

Normal-mode <leader>u: generates one UUID and inserts it at the cursor ("c" = characterwise put).

function M.insert_uuids_visual()
  local start_pos = vim.fn.getpos("'<")
  local end_pos = vim.fn.getpos("'>")
  local start_line, start_col = start_pos[2], start_pos[3]
  local num_lines = end_pos[2] - start_line + 1

  local uuids = generate_uuids(num_lines)
  for i, uuid in ipairs(uuids) do
    local lnum = start_line + i - 1
    local line_content = vim.fn.getline(lnum)
    local updated = line_content:sub(1, start_col - 1) .. uuid .. line_content:sub(start_col)
    vim.fn.setline(lnum, updated)
  end
end

Visual-mode <leader>u: for a selection spanning N lines, generates N UUIDs in one shell call (cheaper than N separate calls) and splices one into each line at the selection's starting column, using string slicing (:sub(...)) to insert without disturbing the rest of each line.

M.rename_file()

function M.rename_file()
  local old_name = vim.fn.expand("%")
  local new_name = vim.fn.input("New file name: ", old_name, "file")
  if new_name ~= "" and new_name ~= old_name then
    vim.cmd("saveas " .. vim.fn.fnameescape(new_name))
    vim.fn.delete(old_name)
    vim.cmd("redraw!")
  end
end

Bound to <leader>n. Prompts for a new name (pre-filled with the current one, with filename completion via the "file" completion type), saves the buffer under the new name, then deletes the old file from disk. fnameescape guards against spaces/special characters breaking the :saveas command.

M.search_current_word() / M.search_visual_selection()

function M.search_current_word()
  local saved_iskeyword = vim.bo.iskeyword
  vim.bo.iskeyword = vim.bo.iskeyword .. ",_"
  local word = vim.fn.expand("<cword>")
  vim.bo.iskeyword = saved_iskeyword

  require("telescope.builtin").grep_string({ search = word })
end

Recall that options.lua globally removes _ from iskeyword (so _ acts as a word boundary for normal word-motion commands like w/e). That's usually what you want, but not here: if the cursor is on get_user_id, a search should grab the whole identifier, not just get. So this function temporarily adds _ back to iskeyword, captures the full word under the cursor with expand("<cword>"), restores the original setting, then hands the full word to Telescope's grep_string.

M.search_visual_selection() does the same job for a visual selection instead of a single word — it yanks the selection into a scratch register ("v", saving/restoring its previous contents) to read out the selected text, then greps for that.

M.find_file_by_word()

Behind <leader><space>. Same iskeyword trick as above to get the full word under the cursor, then builds a search target from it: word.ext using the current buffer's extension (e.g. standing in a .ts file on the word UserService searches for UserService.ts). Useful for jumping between a class and its same-named test/spec/implementation file. Falls through to Telescope's find_files with that as the initial query text.

M.file_cmd() / M.file_name_cmd() — behind <leader>r / <leader><CR>

local executors = {
  py = "!python3 %", js = "!node %", scala = "!scala %",
  sh = "!chmod +x % && ./%", [""] = "!chmod +x % && ./%",
  cpp = "!g++ % && ./a.out && rm a.out", go = "!go run %",
  rs = "!cargo run %", c = "!gcc % && ./a.out && rm a.out",
  tcl = "!tclsh %", ts = "!tsc % && node %:r.js && rm %:r.js",
  hs = "!ghc -o %:r % && ./%:r && rm %:r && rm %:r.hi && rm %:r.o",
  md = "!glow %", cmd = "!glow %",
}

function M.file_cmd()
  vim.cmd("write")
  local ext = vim.fn.expand("%:e")

  if ext == "java" then
    if vim.fn.expand("%"):lower() == "main.java" then
      vim.cmd("!javac % && java main && rm *.class")
    else
      vim.cmd("!mvn test -Dcheckstyle.skip=true -Dtest=" .. vim.fn.expand("%:t:r") .. "Test")
    end
    return
  end

  local cmd = executors[ext]
  if cmd then vim.cmd(cmd)
  else vim.notify("No executor defined for filetype: " .. ext, vim.log.levels.WARN) end
end

A lookup table maps file extension → a shell command to compile-and-run (or just run) the current file, using Vim's %/%:r filename modifiers so the command always refers to whatever file is open. Java gets special-cased outside the table because its behavior branches on the filename itself: a lone main.java gets compiled and run directly with javac/java; anything else is assumed to be a test class living in a Maven project, and gets run with mvn test, targeting just that one test class and skipping checkstyle (so a style nit doesn't block a quick local test run). M.file_name_cmd() is a narrower variant behind <leader><CR> that only knows how to run python3 main.py.

Same dispatch-table pattern as file_cmd, just for test runners: pytest tests for Python, go test for Go.

plugin lua/plugins/treesitter.lua

Syntax highlighting, indentation, and folding, all driven by real parse trees instead of regex.

Note on the API used here: nvim-treesitter's main branch (the actively-developed one as of this writing) rewrote its API — the old require("nvim-treesitter.configs").setup({...}) pattern you'll see in older tutorials no longer exists on this branch. This file uses the current API: .setup() + .install(), plus an explicit vim.treesitter.start() call per filetype. 
local parsers = {
  "java", "python", "lua", "vim", "vimdoc", "bash",
  "json", "yaml", "markdown", "typescript", "tsx", "javascript",
}
local filetypes = {
  "java", "python", "lua", "vim", "help", "sh",
  "json", "yaml", "markdown", "typescript", "typescriptreact", "javascript",
}

Two separate lists on purpose: parser names (what you pass to :TSInstall) don't always match filetype names (what &filetype is actually set to). The vimdoc parser applies to help-filetype buffers; the bash parser applies to sh-filetype buffers; the tsx parser applies to typescriptreact-filetype buffers. Get this mapping wrong and treesitter silently never activates for that filetype.

config = function()
  require("nvim-treesitter").setup()
  require("nvim-treesitter").install(parsers)

  vim.api.nvim_create_autocmd("FileType", {
    pattern = filetypes,
    callback = function(args)
      -- pcall guards the first-ever launch, where a parser may still be
      -- downloading/compiling asynchronously from the install() call above.
      if pcall(vim.treesitter.start, args.buf) then
        vim.wo.foldmethod = "expr"
        vim.wo.foldexpr = "v:lua.vim.treesitter.foldexpr()"
        vim.bo[args.buf].indentexpr = "v:lua.require('nvim-treesitter').indentexpr()"
      end
    end,
  })
end,

install(parsers) kicks off (async) downloads/compiles for any parser not already installed — this needs the tree-sitter CLI on $PATH (installed separately via brew install tree-sitter-cli, since this API compiles grammars from source rather than fetching prebuilt binaries).

Highlighting isn't automatic once a parser exists — each buffer needs an explicit vim.treesitter.start(bufnr) call, which this does on FileType. Wrapped in pcall because on a completely fresh install, the very first time you open (say) a Python file, its parser might still be mid-download when this autocmd fires; pcall swallows that specific race instead of showing a scary error, and it self-heals the next time you open a file of that type. If it succeeds, the same callback also turns on treesitter-based folding and indentation for that buffer.

plenary.nvim is a utility library Telescope is built on (async jobs, path handling, etc.) — not used directly anywhere in this config, just a hard dependency of Telescope itself. telescope-fzf-native.nvim is a small C extension (hence build = "make", compiled on install) that reimplements fzf's fuzzy-matching algorithm natively for faster sorting on large result sets than Telescope's pure-Lua matcher.

Cucumber step definitions

cucumber_language_server (the @cucumber/language-server npm package, installed via Mason like the others) attaches to any buffer with filetype cucumber — which autocmds.lua already maps every *.feature file to — and answers textDocument/definition requests by matching the Gherkin step under the cursor against step-definition regexes/expressions in the project's glue code. Because it's a normal textDocument/definition provider, it needs zero new keymap wiring: the existing <leader>]/<C-]> go-to-definition functions in keymaps.lua already check for any attached LSP client and call vim.lsp.buf.definition()/the raw request — they don't know or care that the "definition" this time is a Java method rather than a variable.

Why root_markers needed widening: the server's own default root marker is just .git. java setup lua/util/jdtls_settings.lua

A single-purpose lookup table: per-project overrides for import ordering, kept separate from after/ftplugin/java.lua so it's an obvious, isolated place to add a new project's convention later.

local DEFAULT_IMPORT_ORDER = { "java", "javax", "org", "com" }

local overrides = {
  -- ["/Users/shane/dev/someproject"] = { "java", "javax", "com.company", "" },
}

function M.import_order(root_dir)
  for path_substring, order in pairs(overrides) do
    if root_dir and root_dir:find(path_substring, 1, true) then
      return order
    end
  end
  return DEFAULT_IMPORT_ORDER
end
Why the override table is empty: jdtls's java.completion.importOrder setting controls the group ordering used by "Organize Imports" and import auto-completion — the natural place to encode a project's checkstyle ImportOrder/CustomImportOrder rule. But as of writing, none of the checkstyle configs on this machine (~/dev/template/checkstyle.xml, ~/dev/developer-toolbox/src/backend/checkstyle.xml) actually define one — only AvoidStarImport/RedundantImport/UnusedImports. DEFAULT_IMPORT_ORDER is a reasonable placeholder until a real one exists. To add a project-specific order later, uncomment/add a line to overrides keyed by any substring of that project's root path.

root_dir:find(path_substring, 1, true) — the trailing true makes this a plain substring search rather than a Lua pattern match, so a path containing special characters like - or . can't accidentally break the lookup.

Lombok

local cmd = { jdtls_cmd, "-data", workspace_dir }
local lombok_jar = vim.fn.stdpath("data") .. "/mason/packages/jdtls/lombok.jar"
if vim.uv.fs_stat(lombok_jar) then
  table.insert(cmd, "--jvm-arg=-javaagent:" .. lombok_jar)
end

Lombok generates methods (getters/setters/builders/equals/toString/etc.) at annotation-processing time from annotations like @Getter/@Data/@Builder — the methods never exist as text anywhere in the source. jdtls can't see them unless Lombok's own Java agent is loaded into jdtls's own JVM (not the project's build JVM) so it can intercept and rewrite the AST the same way `javac` does when Lombok runs as an annotation processor during a real compile. Mason's jdtls package conveniently bundles this exact jar (lombok.jar, sitting right next to the launcher), so no separate download is needed — just point at it.

--jvm-arg is the Mason jdtls launcher script's (a small Python wrapper, not the raw java command) documented way to pass a raw JVM option through to the underlying java process it spawns; it requires the = form (--jvm-arg=-javaagent:..., not a separate argument) per its own --help. The vim.uv.fs_stat check means this degrades gracefully — if the jar isn't there for some reason, jdtls still starts, just without Lombok resolution, rather than failing to start at all.

Verified against a real Lombok class: UserEntity in ~/dev/template has @Getter and defines no getEmail() method anywhere in its source; UserEntityToUserConverter.java calls source.getEmail(). Before this fix that would be an unresolved-method error; after it, hovering the call resolves the full generated signature — String ee.shanel.template.model.entity.UserEntity.getEmail() — with a working source link into UserEntity.java, and the buffer has zero diagnostics.

Organize-imports-on-save

vim.api.nvim_create_autocmd("BufWritePre", {
  pattern = "*.java",
  callback = function(args)
    local clients = vim.lsp.get_clients({ bufnr = args.buf, name = "jdtls" })
    if #clients == 0 then return end

    local client = clients[1]
    local params = vim.lsp.util.make_range_params(0, client.offset_encoding)
    params.context = { diagnostics = {} }
    local resp = client:request_sync("java/organizeImports", params, 2000, args.buf)
    if resp and resp.result then
      vim.lsp.util.apply_workspace_edit(resp.result, client.offset_encoding)
    end
  end,
})

This is the mechanism behind "missing/unused imports get fixed automatically" — it's what replaces the old vim-java-unused-imports vim plugin. On every save of a .java file (before the write happens, hence BufWritePre), if jdtls is attached, it sends jdtls's custom java/organizeImports request and applies whatever edit comes back — adding imports for unambiguous unresolved symbols, removing unused ones, and reordering the rest according to importOrder.

Why this calls the raw LSP request instead of require("jdtls").organize_imports(): nvim-jdtls ships its own organize_imports() helper, but it applies the resulting edit asynchronously — the response comes back after :write has already flushed the old (unorganized) content to disk, which then leaves the buffer marked dirty again right after saving (confusing, and means the file on disk doesn't actually match what you just "saved"). This was caught during testing: a file with two genuinely unused imports, saved via the async helper, still had both imports on disk afterward. Requesting synchronously in BufWritePre (client:request_sync(..., 2000, ...), 2-second timeout) blocks the save just long enough for the edit to land in the buffer before :write proceeds, so what lands on disk is actually correct. Verified by testing directly: a file with unused java.util.List/java.util.ArrayList imports had both removed on save, with the saved file matching the buffer.

One subtlety in the request params: vim.lsp.util.make_range_params(0, ...) — that 0 is the "current window" sentinel (matching how jdtls's own internal helper builds these params), not a buffer number, despite superficially looking like one.

    shell = "/bin/zsh",
  },

Loads lazily on either the :ToggleTerm/:TermExec commands or the <C-\> key — whichever happens first. open_mapping is toggleterm's own internal binding for the same key (so once loaded, it keeps handling <C-\> itself for toggling open/closed).

config = function(_, opts)
  require("toggleterm").setup(opts)

  vim.api.nvim_create_autocmd("TermOpen", {
    pattern = "term://*toggleterm#*",
    callback = function(args)
      local map_opts = { buffer = args.buf }
      vim.keymap.set("t", "<Esc>", [[<C-\><C-n>]], map_opts)
      vim.keymap.set("t", "<C-h>", [[<C-\><C-n><C-W><C-h>]], map_opts)
      -- <C-j/k/l> mirror this for the other directions
    end,
  })

  local Terminal = require("toggleterm.terminal").Terminal
  local ai_term = Terminal:new({
    cmd = "zsh -ic 'ai'",
    direction = "float",
    hidden = true,
  })
  vim.keymap.set("n", "<leader>ai", function()
    ai_term:toggle()
  end, { desc = "Toggle persistent ai (Claude) terminal" })
end,

Without the TermOpen autocmd above, <C-h/j/k/l> inside a terminal buffer would just be sent through to the shell as literal control characters, instead of moving between window splits the way they do everywhere else in this config (see keymaps.lua). The pattern term://*toggleterm#* scopes this specifically to toggleterm's own terminal buffers (identifiable by toggleterm# in their buffer name), so it doesn't affect any other terminal buffer you might open some other way. Each mapping sends <C-\><C-n> first — Neovim's built-in "drop from terminal-insert mode to Normal mode" sequence — before the actual window-movement command, since terminal-mode key input goes straight to the shell process otherwise.

A persistent ai terminal — behind <leader>ai

This is the nvim-native counterpart to bin/tmux-popup (a separate, tmux-level mechanism for the same idea — see below). Rather than calling the generic toggleterm.setup() keymap again, this constructs its own named Terminal object with hidden = true: toggling it closed hides the floating window but does not kill the underlying job, so pressing <leader>ai again reattaches to the exact same running process — same conversation, not a fresh one. Verified directly: opening it, closing it, and reopening it landed on the identical buffer number both times (same_buf=true), and the terminal content showed the real Claude Code welcome banner, confirming the alias actually resolved and launched.

Why cmd = "zsh -ic 'ai'" and not just cmd = "ai": toggleterm spawns its command via Neovim's termopen(), passed as a plain string — which Neovim runs through &shell &shellcmdflag, i.e. a non-interactive zsh -c. Since ai is a plain alias in .zshrc (not a real binary on $PATH), and .zshrc is only sourced for interactive shells, a bare cmd = "ai" would fail to resolve. Forcing -i makes zsh source .zshrc first, so the alias exists by the time it tries to run it — the identical problem, and identical fix, as bin/tmux-popup uses for the same reason (see below). Keeping both indirected through the ai alias rather than hardcoding claude in either place means swapping what ai points to later is a one-line change in .zshrc, not two.
Trade-off vs. the tmux popup: this terminal's persistence is scoped to this one Neovim process — closing the floating window keeps it running, but quitting Neovim (or it crashing) kills it, and it isn't reachable from any other Neovim instance or terminal pane. bin/tmux-popup's session lives at the tmux server level instead, so it survives Neovim entirely, is reachable from any pane via prefix + y, and multiple Neovim instances in the same directory would all reach the same tmux session. Both are wired up; which one you reach for depends on whether you want the conversation tied to "this editing session" or genuinely backgroundable/shareable across panes.

plugin lua/plugins/editing.lua

Three small, config-free tpope plugins, ported as-is from the old .vimrc plugin list.

return {
  { "tpope/vim-surround", event = "VeryLazy" },
  { "tpope/vim-fugitive", cmd = { "Git", "Gdiffsplit", "Gvdiffsplit" } },
  { "tpope/vim-commentary", event = "VeryLazy" },
}
  • vim-surround: add/change/delete surrounding quotes, brackets, tags (cs"', ds", ysiw), etc).
  • vim-fugitive: Git commands from inside Neovim — :Git blame (pairs with gitsigns' quicker inline blame), :Gdiffsplit, :Git as a general front-end.
  • vim-commentary: comment/uncomment lines (gcc, gc + motion).

event = "VeryLazy" is lazy.nvim's "load this shortly after startup finishes, once Neovim is idle" event — used for small plugins that add keymaps/text-objects you might use on the very first keystroke, so they can't wait for something as specific as InsertEnter, but also don't need to block the initial frame the way the colorscheme does. vim-fugitive instead loads only when one of its own commands is actually invoked, since none of its functionality is keymap-driven by default here.

Known caveats

  • black is broken system-wide (not caused by this config) — its shebang points at a removed Homebrew Python. Fix with pipx install black --force or brew install black; <leader>l on Python files will work correctly once it's fixed.
  • Java import order is a placeholder. No checkstyle config on this machine currently defines an ImportOrder/CustomImportOrder module, so jdtls_settings.lua's default (java, javax, org, com) isn't mirroring any real project convention yet — just a reasonable default until one exists.
  • First launch after a fresh clone will spend a few seconds/minutes installing plugins (lazy.nvim), language servers (Mason: pyright, ruff, lua_ls, jdtls), and treesitter parsers, all in the background. Subsequent launches are fast.
